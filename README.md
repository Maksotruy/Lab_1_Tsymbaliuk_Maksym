**# FootballMatches**



**## Тема**



Облік футбольних матчів.



**## Основний тип предметної області**



Основним типом предметної області є \`FootballMatch\`.



Властивості типу:



\- \`Id\` — ідентифікатор матчу;

\- \`HomeTeam\` — команда господарів;

\- \`AwayTeam\` — команда гостей;

\- \`HomeScore\` — кількість голів команди господарів;

\- \`AwayScore\` — кількість голів команди гостей;

\- \`MatchDate\` — дата проведення матчу;

\- \`Stadium\` — стадіон, на якому проводиться матч;

\- \`Status\` — статус матчу.



**## Особливість проєкту**



Особливістю проєкту буде можливість переглядати статистику результатів матчів за певний період. Користувач зможе аналізувати кількість зіграних матчів та забитих голів за вибраний період, що спростить перегляд історії футбольних матчів.

## Лабораторна робота №13 — Конфігурація, логування, публікація та контейнеризація

### Мета роботи

Налаштувати конфігурацію ASP.NET Core, журналювання операцій, автоматичне застосування міграцій, поведінку застосунку в середовищі Production та публікацію Release.

### Конфігурація

Налаштування зберігаються у файлі `FootballMatches/appsettings.json`:

- `ConnectionStrings:Default` — рядок підключення до SQLite;
- `FootballMatches:PageSize` — кількість записів на сторінці (12);
- `FootballMatches:Title` — назва застосунку (`FootballMatches`);
- `Logging:LogLevel` — рівні журналювання.

У вихідному проєкті використовується відносний шлях `Data Source=footballmatches.db`. Файл бази даних слід берегти: повторний запуск з іншої робочої папки може створити окрему порожню базу.

### Журналювання та обробка помилок

Для журналювання операцій застосовується стандартний механізм `ILogger<T>` ASP.NET Core. У Production налаштовано обробник помилок `/Error`, щоб не показувати користувачеві технічні подробиці винятків. Поведінку сторінок для відсутніх записів слід перевірити окремо.

### Автоматичні міграції

Під час запуску застосунок викликає `Database.MigrateAsync()`. Якщо всі міграції вже застосовано, у журналі з'являється повідомлення `No migrations were applied. The database is already up to date.`

### Запуск із чистої копії репозиторію

Необхідні .NET SDK 10 та Git. Після клонування репозиторію перейдіть до каталогу з файлом `FootballMatches.csproj`:

```powershell
git clone <URL-репозиторію>
cd FootballMatches/FootballMatches
dotnet restore
dotnet build
dotnet run
```

Замість `<URL-репозиторію>` вкажіть фактичну адресу репозиторію. Під час першого запуску міграції застосовуються автоматично. Адреса вебзастосунку відображається в терміналі.

### Перевірка Production

Із каталогу з файлом `.csproj`:

```powershell
$env:ASPNETCORE_ENVIRONMENT="Production"
dotnet run -c Release --no-launch-profile
```

Під час перевірки застосунок успішно запустився в Production на `http://localhost:5000`, а журнал підтвердив актуальність міграцій. Окремо слід перевірити, що сторінка помилки не показує стек викликів користувачу.

### Публікація Release

Із каталогу з файлом `FootballMatches.csproj`:

```powershell
dotnet publish -c Release -o ../publish
cd ../publish
dotnet FootballMatches.dll
```

Публікація створює готові файли в каталозі `publish`. Перед запуском перевірте `publish/appsettings.json` і підключення до SQLite. Для локальної перевірки опублікованої версії використовувався шлях до основної бази даних. Такий абсолютний шлях прив'язаний до конкретного комп'ютера і не підходить для розгортання на іншому пристрої без зміни конфігурації.

**Увага:** не додавайте робочі файли `*.db`, їхні резервні копії та локальні абсолютні шляхи до публічного Git-репозиторію. Для перенесення даних використовуйте окрему захищену процедуру резервного копіювання.
