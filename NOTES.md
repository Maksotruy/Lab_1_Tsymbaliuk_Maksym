# Робочі нотатки

Для `HomeScore` та `AwayScore` обрано тип `int`, оскільки кількість голів є цілим невід'ємним числом.

Для `MatchDate` обрано `DateOnly`, оскільки для обліку матчу потрібна саме дата проведення без часу.

Для `Stadium` використано `string?`, оскільки інформація про стадіон може бути відсутньою.

Для `Status` використано `enum MatchStatus`, оскільки статус матчу має обмежений набір можливих значень: запланований, завершений або скасований.
## Entity Framework Core та SQLite

Для роботи з базою даних використано Entity Framework Core та SQLite.

Створено контекст `FootballMatchesContext`, який містить `DbSet<FootballMatch> FootballMatches`.

Для підключення SQLite використано базу даних `footballmatches.db`.

Створено першу міграцію `Init` та застосовано її до бази даних за допомогою команд `dotnet ef migrations add Init` і `dotnet ef database update`.

У поточній моделі немає властивостей типу `decimal`, тому додаткове перетворення типів для SQLite не потрібне. Таке перетворення могло б знадобитися, якби модель містила десяткові значення типу `decimal`, наприклад ціну або іншу грошову величину.

## Лабораторна робота №4. Генератор сторінок для роботи із записами

### 1. Директива @page

Директива `@page` визначає маршрут, за яким відкривається Razor-компонент. У моєму проєкті сторінка перегляду футбольних матчів доступна за адресою `/footballmatches`.

### 2. IDbContextFactory

`IDbContextFactory<FootballMatchesContext>` використовується для створення контексту бази даних. Завдяки цьому сторінки можуть працювати із записами футбольних матчів у SQLite.

### 3. Параметр Items компонента QuickGrid

Параметр `Items` визначає записи, які відображаються в таблиці. Для пагінації використано методи `Skip()` і `Take()`, які дозволяють показувати по 10 матчів на сторінці.

### 4. EditForm, FormName та SupplyParameterFromForm

`EditForm` використовується для створення та редагування футбольних матчів. `FormName` задає назву форми, а `[SupplyParameterFromForm]` дозволяє отримувати введені користувачем дані.

### 5. OnValidSubmit та NavigateTo

`OnValidSubmit` викликає метод збереження після успішної перевірки форми. `NavigateTo` забезпечує повернення користувача до списку футбольних матчів після створення або редагування запису.

### Результат роботи

У ході лабораторної роботи створено сторінки для додавання, перегляду, редагування та видалення футбольних матчів. Для відображення записів використано QuickGrid. Реалізовано пагінацію з відображенням 10 записів на сторінці. База даних SQLite забезпечує збереження інформації між запусками програми.

## Лабораторна робота №5. Власний компонент Blazor

### Створення власного компонента

У ході лабораторної роботи було створено власний компонент `FootballMatchCard.razor`, який призначений для відображення інформації про футбольний матч.

Компонент розміщено в каталозі `Components`. Він дозволяє відображати назви команд, рахунок, дату проведення матчу, стадіон, статус та ідентифікатор запису.

### Передавання даних через параметри

Для передавання інформації про футбольний матч використано параметр `FootballMatch` типу `FootballMatch`.

Параметр позначено атрибутами `[Parameter]` та `[EditorRequired]`. Перший дозволяє передавати дані від батьківського компонента, а другий вказує, що параметр обов'язково потрібно зазначити під час використання компонента.

### Параметри вигляду

Для налаштування зовнішнього вигляду компонента додано два параметри:

- `Caption` — визначає заголовок картки футбольного матчу.
- `ShowDetails` — визначає, чи потрібно показувати додаткову інформацію про матч.

Завдяки цим параметрам один компонент можна використовувати для різних способів відображення даних.

### Використання компонента на сторінках

Компонент `FootballMatchCard` використано на двох сторінках застосунку:

- `Details.razor` — компонент відображає повну інформацію про матч із параметром `ShowDetails="true"`.
- `Delete.razor` — компонент відображає скорочену інформацію про матч із параметром `ShowDetails="false"`.

На обох сторінках повторювану розмітку замінено викликом власного компонента.

### Висновок

Під час виконання лабораторної роботи було розглянуто принципи створення та використання компонентів Blazor. Створено компонент `FootballMatchCard`, реалізовано передавання даних через параметри та налаштування його вигляду.

Використання власного компонента дозволило зменшити дублювання коду, спростити структуру сторінок і забезпечити повторне використання розмітки в застосунку `FootballMatches`.

## Лабораторна робота №6. Перевірка введених даних

### Атрибути перевірки

У моделі `FootballMatch` додано атрибути `Required`, `StringLength` та `Range` із власними повідомленнями українською мовою.

Вони забезпечують перевірку обов'язкових назв команд, максимальної довжини текстових полів і допустимого діапазону кількості голів.

### Перевірка між властивостями

На сторінках `Create.razor` та `Edit.razor` реалізовано додаткові перевірки:

- Домашня та гостьова команди не можуть бути однаковими.
- Запланований матч повинен мати рахунок 0:0.
- Дата проведення матчу повинна бути коректною.

Якщо введені дані не відповідають правилам, збереження скасовується, а користувач отримує повідомлення українською мовою.

### Унікальний індекс

У класі `FootballMatchesContext` створено унікальний індекс за властивостями `HomeTeam`, `AwayTeam` і `MatchDate`.

Індекс запобігає збереженню двох футбольних матчів з однаковими значеннями цих властивостей.

Для внесення змін до структури бази даних створено міграцію `UniqueFootballMatch`.

### Обробка помилок збереження

На сторінках створення та редагування реалізовано конструкцію `try/catch`.

Для виявлення порушення унікальності використано `DbUpdateException` та код SQLite `2067`.

У разі виникнення помилки користувач отримує зрозуміле повідомлення замість сторінки з технічною помилкою.

### Висновок

Під час лабораторної роботи було реалізовано перевірку введених даних у застосунку `FootballMatches`. Використано атрибути DataAnnotations, перевірки між властивостями, унікальний індекс SQLite та обробку винятків EF Core.

Реалізовані механізми допомагають запобігати збереженню некоректних і повторюваних записів та покращують взаємодію користувача із застосунком.


# Лабораторна робота №7

## Тема: Зв'язки між сутностями та робота з довідниками в Blazor

### Мета роботи

Навчитися створювати зв'язки між сутностями за допомогою Entity Framework Core, використовувати зовнішні ключі, реалізовувати CRUD-операції для довідників та інтегрувати пов'язані дані у вебзастосунок Blazor.

### Хід виконання роботи

**1. Створення сутностей Team і Stadium**

У проєкті FootballMatches створено дві додаткові сутності:

- Team — зберігає інформацію про футбольні команди, зокрема назву команди та країну.
- Stadium — зберігає інформацію про футбольні стадіони, зокрема назву стадіону та місто.

Ці сутності використовуються як довідники для створення футбольних матчів.

**2. Налаштування зв'язків між сутностями**

У моделі FootballMatch реалізовано зовнішні ключі:

- HomeTeamId — посилання на домашню команду.
- AwayTeamId — посилання на гостьову команду.
- StadiumId — посилання на стадіон.

Для кожного матчу визначаються дві команди та один стадіон.

**3. Обґрунтування напрямку зв'язків**

Використано зв'язки типу «один до багатьох».

Одна футбольна команда може брати участь у багатьох матчах як домашня або гостьова. Водночас кожен матч має одну домашню та одну гостьову команду.

Один стадіон може використовуватися для проведення багатьох матчів, але кожен окремий матч пов'язаний з одним стадіоном.

Такий підхід дозволяє уникнути дублювання інформації та забезпечує цілісність даних.

**4. Налаштування Entity Framework Core**

У FootballMatchesContext додано DbSet для Team і Stadium.

Зв'язки між FootballMatch, Team і Stadium налаштовано за допомогою Fluent API.

Для пов'язаних записів використано DeleteBehavior.Restrict, щоб запобігти випадковому видаленню команд або стадіонів, які використовуються у матчах.

**5. Створення та застосування міграції**

Після зміни моделей створено міграцію Entity Framework Core та оновлено базу даних SQLite.

У базі даних створено таблиці для команд і стадіонів та налаштовано зовнішні ключі.

**6. Реалізація CRUD для довідників**

Створено сторінки для виконання основних операцій:

- Create — додавання нових команд і стадіонів.
- Read — перегляд списку та інформації про записи.
- Update — редагування даних.
- Delete — видалення записів з урахуванням зв'язків.

Довідники заповнено футбольними командами та стадіонами.

**7. Оновлення форм FootballMatch**

У формах створення та редагування матчів реалізовано випадаючі списки для вибору домашньої команди, гостьової команди та стадіону.

Під час збереження матчу використовуються відповідні зовнішні ключі.

Додано перевірку правильності вибору команд, щоб одна команда не могла одночасно бути домашньою та гостьовою.

**8. Відображення пов'язаних даних**

На сторінках FootballMatches відображаються назви команд і стадіонів замість числових ідентифікаторів.

Для завантаження пов'язаних сутностей використовується Entity Framework Core.

**9. Оновлення документації**

У README.md додано Mermaid-діаграму, яка відображає структуру сутностей та зв'язки між ними.

### Висновок

Під час виконання лабораторної роботи №7 було реалізовано зв'язки між сутностями FootballMatch, Team і Stadium. Створено довідники команд і стадіонів, налаштовано зовнішні ключі та поведінку видалення, реалізовано CRUD-операції. Форми роботи з матчами доповнено випадаючими списками для вибору пов'язаних даних. У результаті структура бази даних стала більш упорядкованою, а робота із футбольними матчами — зручнішою.
